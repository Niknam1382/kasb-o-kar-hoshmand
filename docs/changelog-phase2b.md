# تغییراتِ فازِ ۲-ب (RBAC ادمین‌ها، افزودنِ گروهیِ محصول از اکسل، استردادِ کیف‌پول، ابزارهایِ dev)

این فایل، جداگانه از `changelog-phase1-recovery.md`، مخصوصِ فازِ ۲-ب هست — چون
فازِ ۲-ب چهار زیربخشِ نسبتاً مستقل داره (RBAC / اکسل / استردادِ کیف‌پول /
dev-tools) و هرکدوم زیپِ تست‌شونِ خودشون رو می‌گیرن. زیربخش‌های بعدی به همین
فایل اضافه می‌شن.

## زیربخشِ ۱: RBAC ادمین‌ها (کامل — منتظرِ نتیجه‌ی تستِ کاربر)

### چرا
قبلِ این، همه‌چیزِ پنلِ ادمین پشتِ یه چکِ تخت بود: «آیا این آیدیِ تلگرام توی
`ADMIN_TELEGRAM_IDS` (در `.env`) هست؟» — یعنی یا دسترسیِ کامل، یا هیچی. برای
اینکه بشه به یه نفر دسترسیِ محدودتر داد (مثلاً یه همکارِ پشتیبانی که فقط باید
پرداخت تایید کنه و فروشگاه‌دار مدیریت کنه، بدونِ دسترسی به تنظیماتِ قیمت یا
کلیدهایِ AI)، یه سطحِ دومِ دسترسی («ادمینِ عملیاتی») اضافه شد.

### طراحیِ نهایی (تاییدشده با کاربر)
دو سطح:
- **سوپرادمین** — همون لیستِ ثابتِ `ADMIN_TELEGRAM_IDS` در `.env`، بدونِ تغییر.
  دسترسیِ کامل: تنظیماتِ قیمت/تخفیف، تنظیماتِ کلیدها، استخرِ کلیدهایِ AI، و
  خودِ مدیریتِ ادمین‌ها (افزودن/حذفِ ادمینِ عملیاتی).
- **ادمینِ عملیاتی** — سطحِ جدید، ذخیره‌شده توی جدولِ `admin_roles`، فقط
  سوپرادمین می‌تونه اضافه/حذفش کنه. دسترسی به: صفِ تاییدِ پرداخت، مدیریتِ
  فروشگاه‌دارها (شاملِ هدیه‌ی کیف‌پول)، پیامِ همگانی، مدیریتِ کانال‌هایِ اجباری،
  نگهبانِ محتوا، آمارِ سراسری، گزارشِ ممیزی.

اگه جدولِ `admin_roles` خالی بمونه، رفتار دقیقاً مثلِ قبل از RBAC می‌مونه —
سازگاریِ کاملِ عقب، هم‌الگو با استخرِ کلیدهایِ AI در فازِ ۲-الف.

### چیکار شد (فنی)
- **`app/database/models.py`**: مدلِ جدیدِ `AdminRole` (`telegram_id` یکتا،
  `role`، `granted_by_telegram_id`، `created_at`) + اِنامِ `AdminRoleType`
  (فعلاً فقط `operator`) + دو مقدارِ جدید توی `AuditEventType`
  (`operator_admin_granted`, `operator_admin_revoked`).
- **مایگریشنِ جدید** (`db68ee15015b`, بعد از `c84a9c3c7f34`): می‌سازهٔ جدولِ
  `admin_roles`.
- **`app/services/admin_role_service.py`** (جدید): `grant_operator`,
  `revoke`, `is_operator`, `get_all`, `get_by_id`, `get_by_telegram_id`.
- **`app/bots/main_bot/filters.py`**: `IsSuperAdmin` جدید (فقط چکِ `.env`) +
  `IsAdmin` گسترده‌شده (چکِ `.env` **یا** جدولِ `admin_roles`، از طریقِ
  `session`ی که `DbSessionMiddleware` سرتاسری — رویِ `dispatcher.update` —
  تزریق می‌کنه؛ نبودِ `session` محافظه‌کارانه یعنی فقط سوپرادمین).
- **`app/bots/main_bot/handlers/admin.py`**: یه `super_router` جدید (فیلترِ
  `IsSuperAdmin` روی کلِ روتر) کنارِ `router`ِ قبلی (حالا با `IsAdmin`ِ
  گسترده‌شده). بخش‌هایِ «تنظیماتِ قیمت و تخفیف»، «تنظیماتِ کلیدها»، و «استخرِ
  کلیدهایِ AI» (۳۲ هندلر) به `super_router` منتقل شدن؛ بقیه‌ی بخش‌ها
  (کانال‌ها، پرداخت، فروشگاه‌دارها، پیامِ همگانی، آمار، نگهبانِ محتوا، گزارشِ
  ممیزی) دستِ‌نخورده روی `router` موندن. + فیچرِ جدیدِ «👑 مدیریتِ ادمین‌ها»
  (افزودن با آیدیِ عددی، مشاهده، حذف) روی `super_router`، با ردِ موارد مرزی:
  آیدیِ سوپرادمینِ موجود، آیدیِ تکراری، ورودیِ غیرعددی. هر افزودن/حذف توی
  گزارشِ ممیزی هم ثبت می‌شه.
- **`app/bots/main_bot/keyboards.py`**: `admin_panel_keyboard(is_super_admin)`
  حالا یه پارامتر می‌گیره — ادمینِ عملیاتی اصلاً دکمه‌های حساس رو نمی‌بینه
  (نه اینکه ببینه و بعد بلاک بشه). + دو کیبوردِ جدید برای فهرست/جزئیاتِ
  ادمین‌های عملیاتی.
- **`app/bots/main_bot/texts.py`**: متن‌هایِ جدیدِ `ADMIN_ROLES_*` + برچسبِ
  گزارشِ ممیزی برایِ دو رویدادِ جدید.
- **`app/bots/main_bot/states.py`**: `AdminRoleStates` (یه state:
  `waiting_telegram_id`).
- **`app/bots/main_bot/handlers/panel.py`**: `/cancel` حالا ادمینِ عملیاتی
  رو هم تشخیص می‌ده (قبلاً فقط چکِ `.env` بود، پس ادمینِ عملیاتی کیبوردِ
  فروشگاه‌دار رو می‌دید).
- **`app/bots/main_bot/router.py`**: `super_router` ثبت شد؛ دکمه‌ی جدید به
  `_KNOWN_MENU_BUTTONS` اضافه شد.

### یه فیکسِ کوچیکِ جانبی (هم‌جا، چون داشتم دقیقاً همین لیست رو دست می‌زدم)
«🛡 نگهبانِ محتوا» و «📜 گزارشِ ممیزی» هیچ‌وقت به `_KNOWN_MENU_BUTTONS` اضافه
نشده بودن — همون کلاس‌باگی که «🔑 استخرِ کلیدهایِ AI» رو توی فیکس‌۲ لازم داشت
(فشردنِ دکمه وسطِ یه FSM state درست escape نمی‌شد). چون خطرِ نزدیک به صفره و
دقیقاً همون فایل/همون لیسته، همین‌جا هم اضافه شدن.

### تست
**`tests_manual/test_admin_rbac.py`** (جدید، به `run_all_tests.py` هم اضافه
شد) — ۹ تست: تفاوتِ کیبورد بینِ دو سطح، بلاک‌شدنِ ادمینِ عملیاتی از بخش‌هایِ
سوپرادمین (بدونِ پاسخ، نه خطا)، دسترسیِ ادمینِ عملیاتی به بخش‌هایِ خودش،
بلاک‌ماندنِ کاملِ کاربرِ غیرادمین (سازگاریِ عقب)، فلوِ کاملِ افزودن+مشاهده+حذف
از داخلِ ربات، و سه موردِ مرزی (سوپرادمینِ موجود، آیدیِ تکراری، ورودیِ
غیرعددی).

همه‌ی فایل‌هایِ تغییریافته/جدید با `py_compile` چک شدن (بدونِ خطایِ سینتکسی)،
ولی مثلِ همیشه، تاییدِ واقعی با اجرایِ کاملِ تست‌ها روی Docker هست — پایینِ
همین صفحه.

**✅ تاییدشده روی Dockerِ کاربر (۲۰۲۶-۰۹-۲۳)**: `docker compose run --rm bot
python3 tests_manual/run_all_tests.py` → ۳۵/۳۵ فایل پاس، ۱۵۰/۱۵۰ تستِ
جداگانه پاس، شاملِ `test_admin_rbac.py` (۹ تست). به‌علاوه، ۷ فایلِ تستی که
توی یه سشنِ قبلیِ فازِ ۲-الف fail می‌شدن (debounce، تحلیلِ عکس/صدا،
تطبیقِ آیدیِ محصولِ سفارش، یکپارچگیِ کیف‌پول، قانونِ WARNِ نگهبانِ محتوا،
fallbackِ استخرِ خالیِ AI) الان همه پاس می‌شن — قبل از شروعِ این چت رفع شده
بودن.

## زیربخشِ ۲: افزودنِ گروهیِ محصول از اکسل (کامل — منتظرِ نتیجه‌ی تستِ کاربر)

### چرا
افزودنِ محصول فقط از طریقِ فلوِ تک‌به‌تکِ «➕ افزودن محصول جدید» ممکن بود —
برایِ فروشگاه‌دارهایی که ده‌ها محصول دارن، یعنی ده‌ها بار تکرارِ همون پنج
سوال. هدف: یه راهِ گروهی از طریقِ فایلِ اکسل.

### طراحی (فرض‌هایِ صریح — کاربر گفته برایِ تصمیماتِ پیاده‌سازی فرض کن و پیش
برو، نه اینکه هربار بپرس)
- **فلو**: دکمه‌ی جدید «📥 افزودن گروهی از اکسل» (کنارِ «➕ افزودن محصول
  جدید» توی فهرستِ محصولات) → ربات یه فایلِ قالبِ خالی (فقط هدرِ استایل‌خورده،
  دقیقاً هم‌سبک با خروجی‌هایِ اکسلِ موجود) می‌فرسته → فروشگاه‌دار پرش می‌کنه و
  برمی‌گردونه → ربات پارس/اعتبارسنجی می‌کنه و یه **پیش‌نمایش** نشون می‌ده (چند
  ردیف معتبره، کدوم ردیف‌ها مشکل دارن و چرا) → فروشگاه‌دار صریحاً تایید یا
  انصراف می‌ده → فقط بعدِ تایید، محصولات ساخته می‌شن. این مرحله‌ی
  «پیش‌نمایش+تاییدِ صریح» عمداً هم‌روحِ «بازطراحیِ سفارش‌گیری»یِ تاییدشده‌ست
  (تاییدِ صریح قبل از نهایی‌شدن، نه حدس‌زدنِ خاموش)؛ برایِ همین بدونِ پرسیدن
  همینو انتخاب کردم.
- **ستون‌هایِ قالب** (ترتیب/برچسب ثابت، جابه‌جایی یعنی داده‌ی غلط خونده
  می‌شه): نامِ محصول (الزامی) / توضیحات (اختیاری) / قیمت به تومان (الزامی) /
  موجودی (اختیاری، خالی = نامحدود — دقیقاً هم‌معنیِ «رد شدن» توی فلوِ تکی).
- **عکس پشتیبانی نمی‌شه** — چون file_id تلگرام از طریقِ اکسل قابلِ واردکردن
  نیست. بعدِ افزودنِ گروهی، هر محصول جداگانه قابلِ ویرایش برایِ افزودنِ عکسه.
- **اتمیک**: همه‌چیز روی یه session ی مشترک (که فقط یه‌بار در انتهایِ همون
  آپدیت commit می‌شه)، پس یا همه‌ی ردیف‌هایِ معتبر اضافه می‌شن یا هیچ‌کدوم.
- **سقفِ ۵۰۰ ردیف** در هر فایل + سقفِ ۵ مگابایت رویِ حجمِ خودِ فایل
  (محافظه‌کارانه، صرفاً محافظت از فایل‌هایِ بیش‌ازحد بزرگ).
- ردیف‌هایِ کاملاً خالی (ته‌ماندهٔ شیت) بی‌سروصدا نادیده گرفته می‌شن، نه
  به‌عنوانِ خطا؛ نامِ تکراری بینِ محصولات چک/ردّ نمی‌شه (هم‌رفتار با فلوِ تکی).

تاییدِ نهایی، مثلِ همیشه، با اجرایِ کاملِ تست‌ها روی Dockerِ کاربره — منتظرِ
نتیجه.

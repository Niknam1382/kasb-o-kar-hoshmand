# راهنمایِ کاملِ استقرار و ارتقایِ «کسب‌وکار هوشمند»

### نسخهٔ ۱ · ۱۴۰۵-۰۸-۱۴ (۲۰۲۶-۱۱-۰۵) · نوشته‌شده برایِ کسی که اولین سرور را می‌خرد

این سند به زبانِ ساده نوشته شده و فرض نمی‌کند برنامه‌نویس هستی. هر عددی که می‌بینی یا **اندازه‌گیری‌شده** است
(با برچسبِ «اندازه‌گیری‌شده»)، یا از آن عدد با یکِ فرضِ مشخص **محاسبه** شده («محاسبه‌شده با فرضِ …»)، یا فقط
**تخمین** است («تخمین»). جایی که نمی‌دانیم، صریح نوشته‌ایم «نسنجیده شده».

هدفِ این سند: سه سؤال را جواب بدهد — ۱) چه سروری بخرم؟ ۲) چطور نصبش کنم؟ ۳) وقتی کاربران زیاد شد چه کار کنم؟

---

## ۱) واژه‌نامهٔ کوتاه (همین شش کلمه کافی است)

| واژه | یعنی چه |
|---|---|
| **رباتِ اصلی (پنل)** | رباتِ تلگرامی که فروشگاه‌دار با آن محصولات، سفارش‌ها و کیف‌پول را مدیریت می‌کند. |
| **رباتِ فروشگاهی** | رباتی که با توکنِ خودش برایِ *یک* فروشگاه کار می‌کند و به مشتری جواب می‌دهد. |
| **فروشگاه‌دار** | انسانی که پنل را دارد و پولِ اشتراک/اعتبار می‌دهد. مصرفِ رم و تعدادِ اتصال‌ها با این عدد بالا می‌رود. |
| **مشتریِ فعال** | کسی که واقعاً در ماه پیام می‌دهد. مصرفِ AI و دیتابیس با این عدد بالا می‌رود. |
| **پروژه/سرویس داکر** | برنامه با دو کانتینر بالا می‌آید: `db` (دیتابیس) و `bot` (خودِ برنامه). |
| **حجم (volume)** | جایی که دادهٔ دیتابیس رویِ دیسکِ سرور نگه داشته می‌شود؛ با پاک‌کردنِ آن همه‌چیز می‌رود. |

یک چیز که باید همیشه یادت باشد: **توکن‌ها راز هستند**. توکنِ رباتِ تلگرام، توکنِ درگاهِ بله‌پی، کلیدِ AI و رمزِ
دیتابیس فقط در فایلِ `.env` رویِ سرور شما هستند و هیچ‌جا (لاگ، پیام، مستندات، عکسِ صفحه‌نما) چاپ نمی‌شوند.

## ۲) چه سروری بخرم؟ (جدولِ مقیاس)

| # | مقیاس | vCPU | رم | دیسک | دیتابیس | برچسبِ عدد |
|---|---|---|---|---|---|---|
| ۱ | تست و راه‌اندازی — تا ~۲۰ فروشگاه‌دار | ۲ | ۲ گیگ | ۲۰ گیگ SSD | همان ماشین | اندازه‌گیری‌شده در محیطِ توسعه: با ۳ فروشگاه‌دار ~۰٫۹ گیگ کل مصرف |
| ۲ | **امروز، برایِ شروعِ واقعی** — تا ~۱۰۰ فروشگاه‌دار فعال | ۴ | ۴ تا ۶ گیگ | ۴۰ گیگ NVMe | همان ماشین | تخمین؛ بامِ کد در این لایه اندازه‌گیری‌شده است (بخشِ ۸) |
| ۳ | رشد — ~۱۰۰ فروشگاه‌دارِ پرمصرف یا چند صد مشتریِ هم‌زمان | ۴ تا ۸ | ۸ گیگ | ۸۰ گیگ NVMe | **هاستِ جدا** (مهم‌ترین کارِ این لایه) | تخمین |
| ۴ | ~۵۰۰ رویدادِ هم‌زمان | ۸ | ۱۶ گیگ | ۱۵۰ گیگ NVMe | ۴ هسته / ۸ گیگ اختصاصی + PgBouncer | امروز با یکِ پروسه ممکن نیست (بخشِ ۹) |
| ۵ | ~۱۰۰۰ رویدادِ هم‌زمان | ۱۶ | ۳۲ گیگ | ۳۰۰ گیگ NVMe + کپیِ خواندنی | ۸ هسته / ۳۲ گیگ | نیازمندِ بازطراحی (وب‌هوک + صفِ جدا) |

**اگر مقیاست را «تعدادِ مشتری» می‌دانی نه «تعدادِ فروشگاه»:** تجربهٔ این پروژه نشان می‌دهد هر فروشگاهِ فعالِ
واقعی معمولاً ۲۰ تا ۳۰۰ مشتریِ ثبت‌شده دارد و از آن‌ها ۲۰ تا ۶۰ مشتریِ *فعال* در ماه. پس:
**تعدادِ مشتریِ فعال ÷ ۳۰ ≈ تعدادِ فروشگاه** (محاسبه با همین فرض).

| مشتریِ فعالِ ماهانه | فروشگاهِ تقریبی | سرورِ پیشنهادی |
|---|---|---|
| ~۱٬۰۰۰ | ~۳۳ | لایهٔ ۱ تا ۲ (۲ تا ۴ هسته / ۴ گیگ) |
| ~۵٬۰۰۰ | ~۱۷۰ | لایهٔ ۲ (۴ هسته / ۶ گیگ) |
| ~۱۵٬۰۰۰ | ~۵۰۰ | لایهٔ ۳ تا ۴ (۸ هسته / ۸ تا ۱۶ گیگ + دیتابیسِ جدا) |
| ~۵۰٬۰۰۰ | ~۱٬۷۰۰ | لایهٔ ۵ (۱۶ هسته / ۳۲ گیگ) + وب‌هوک و صفِ جدا |

**کجا بخری (کدام کشور/دیتاسنتر):** اگر مشتریانت هم تلگرام و هم بله دارند، سرورِ **خارج از ایران** (آلمان/هلند/ترکیه) بخر:
دسترسیِ پایدار به `api.telegram.org` و `tapi.bale.ai`. سرورِ داخلِ ایران به بله نزدیک‌تر و ارزان‌تر است، ولی
وصل‌شدنِ آن به تلگرام معمولاً ناپایدار است.

**سه اشتباهِ رایج در خرید:** ۱) رمِ کم + سوآپ (اولین قربانی کشِ دیتابیس است و همه‌چیز کند می‌شود) ۲) دیسکِ HDD
به‌جایِ NVMe ۳) IP اشتراکیِ سیاه‌شده (تلگرام از همان IP را بلاک می‌کند؛ قبل ازِ خرید با
`curl -s https://api.telegram.org` امتحان کن؛ در عملِ ساده‌تر: `docker compose up` و دیدنِ لاگِ polling).

## ۴) نصبِ قدم‌به‌قدم (کپی‌کردنی)

```bash
# ۰) داکر و داکر کومپوز
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER && newgrp docker
docker --version && docker compose version

# ۱) فایروال: فقط SSH باز باشد. پورتِ ۸۰۰۰ را بیرون باز نکن، مگر وب‌هوک بخواهی
sudo ufw allow OpenSSH && sudo ufw enable

# ۲) کد
git clone <آدرسِ مخزنِ تو> kasb-o-kar-hoshmand
cd kasb-o-kar-hoshmand

# ۳) تنظیمات (فایلِ نمونه را کپی کن و بعد مقدارها را از پنل‌هایِ مربوطه خودت بگذار)
cp .env.docker.example .env
nano .env

# ۴) اولین بالا آمدن (دیتابیس + ربات)
docker compose up -d --build

# ۵) سلامت
docker compose ps
docker compose exec -T bot python -c "import urllib.request;print(urllib.request.urlopen('http://127.0.0.1:8000/health',timeout=5).status)"
docker compose logs --tail=40 bot
```

**چطور بفهمی درست کار می‌کند:** `docker compose ps` هر دو سرویس را `Up … (healthy)` نشان می‌دهد، `/health` عددِ
۲۰۰ می‌دهد و در لاگِ `bot` این خط را می‌بینی: `Run polling for bot @…`. اگر به‌جایِ آن خطایِ شبکه می‌بینی،
یعنی سرور به `api.telegram.org` نمی‌رسد (بخشِ ۱۲).

**نامِ پوشه مهم است:** نامِ پروژهٔ داکر از نامِ پوشه ساخته می‌شود و حجمِ دیتابیس هم به همان نام است
(`kasb-o-kar-hoshmand_postgres_data`). اگر پوشه را عوض/تغییرنام کنی، داکر یکِ دیتابیسِ **خالیِ** تازه می‌سازد و
همه‌چیز «پاک شده» به‌نظر می‌آید (داده در حجمِ قبلی سالم است). در `docker-compose.yml` خطِ `name:` این را قفل
کرده‌ایم؛ اگر جابه‌جا کردی، همان نام را نگه دار یا با `docker compose -p kasb-o-kar-hoshmand …` اجرا کن.

## ۵) `.env` — فقط این‌ها را باید عوض کنی

| کلید | اگر خالی بماند چه می‌شود | نکته |
|---|---|---|
| `MAIN_BOT_TOKEN` | برنامه بالا نمی‌آید (خطایِ صریحِ تنظیمات) | توکنِ رباتِ پنل از BotFather |
| `ENCRYPTION_KEY` | برنامه بالا نمی‌آید | **بعد ازِ اولین استفاده هرگز عوضش نکن**: با کلیدِ تازه هیچ توکن/رمزِ ذخیره‌شده بازخوانی نمی‌شود |
| `ADMIN_TELEGRAM_IDS` | پنلِ ادمین دست‌یافتنی نیست | شناسهٔ عددیِ خودت، با کاما جدا کن |
| `DATABASE_URL` | لازم نیست؛ در compose از سرویسِ `db` ساخته می‌شود | فقط اگر دیتابیسِ جدا گرفتی عوضش کن |
| `AI_API_KEY` / مدل‌ها | رباتِ چت جواب نمی‌دهد (فقط فروش و پنل کار می‌کند) | کلیدها را می‌توانی از پنلِ ادمین هم ثبت کنی (استخرِ کلید) |
| `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` | مقادیرِ فعلیِ کد (۲۵ و ۰) خوب کار می‌کند | بخشِ ۹: `overflow` را صفر نگه دار |
| `RUN_MODE` | پیش‌فرض `polling` | برایِ مقیاسِ بالا بعداً `webhook` (بخشِ ۹) |
| `BOT_MEM_LIMIT` | پیش‌فرض `1g` | برایِ ~۵۰۰ فروشگاه `2g` |
| `FSM_STORAGE` | پیش‌فرض `memory` | `postgres` اگر می‌خواهی چک‌اوتِ نیمه‌کاره با ری‌استارتِ برنامه نشکند |
| `METRICS_TOKEN` | `/metrics` بی‌دسترسی می‌ماند (امن‌تر) | فقط برایِ مانیتورینگ باز کن |

⚠️ فایلِ `.env` را هرگز commit نکن و از صفحه‌نمایِ رایانه‌ات رویِ آن عکس نگیر. اگر جایی توکن چاپ شد، از همان سرویس
revoke و تازه‌اش را ثبت کن.

## ۶) بکاپ و بازگردانی (این‌جا است که کسب‌وکار زنده می‌ماند)

```bash
# یک بکاپِ فشرده، با تاریخِ امروز
mkdir -p ~/backups
docker compose exec -T db pg_dump -U postgres -Fc kasbokar > ~/backups/kasbokar-$(date +%F-%H%M).dump

# بازگردانی در سرورِ تازه (مقدارهایِ DATABASE_URL را از .env بخوان)
docker compose exec -T db pg_restore -U postgres -d kasbokar --clean --if-exists < ~/backups/kasbokar-…dump
```

خودکارش کن (`crontab -e`، هر شب ساعت ۰۲:۳۰):

```cron
30 2 * * * cd /home/USER/kasb-o-kar-hoshmand && docker compose exec -T db pg_dump -U postgres -Fc kasbokar > /home/USER/backups/kasbokar-$(date +\%F).dump && find /home/USER/backups -name '*.dump' -mtime +14 -delete
```

عددهای واقعیِ همین نصب (اندازه‌گیری‌شده): با ۳ فروشگاه‌دار یکِ بکاپ ۱۳۰ تا ۱۸۰ کیلوبایت است؛ دیتابیسِ ~۱ گیگی
≈ ۲۵۰ مگابایت فشرده ⇒ ۱۴ نسخه ≈ ۳٫۵ گیگ. **بکاپی که یک‌بار بازگردانی نشده، بکاپ نیست:** ماهی یک‌بار رویِ یک
سرور/کانتینرِ بی‌خطر بازگردانش کن و `alembic current` را با کدِ تازه مقابله کن.

## ۷) آپدیتِ کد و برگشتِ امن

```bash
git pull
docker compose build bot
docker compose up -d              # داکر فقط کانتینرِ عوض‌شده را دوباره می‌سازد
docker compose logs --tail=30 bot
```

قاعده‌هایِ این پروژه که در آپدیت به کارت می‌آید:

- مایگریشن‌ها **افزوندی** هستند (هیچ ستون/جدولی حذف نمی‌شود) ⇒ برگشتِ کدِ قدیمی رویِ دیتابیسِ تازه معمولاً
  کار می‌کند. قبل ازِ هر آپدیت بکاپ بگیر.
- بعد ازِ آپدیت چک کن که فقط **یک** هدِ مایگریشن باشد:
  `docker compose run --rm bot alembic heads` (باید یک خط بدهد).
- اگر خواستی به نسخهٔ قبل برگردی: `git checkout <تگ/کامیت>` و `docker compose up -d --build`. دیتابیس را
  down **با `-v`** نزن؛ آن کل داده است.
- کد داخلِ ایمیج است (volume mount ندارد): هر تغییرِ کد = `build` دوباره. این را اگر یادت برود، تست‌ها
  کدِ کهنه را می‌سنجند و عددِ گمراه‌کننده می‌دهند.

## ۸) بامِ واقعیِ همین کد چقدر است (تا حدِ نسنجیده، صادقانه)

عددهایِ این بخش از سه سندِ اندازه‌گیریِ خودِ پروژه است: `SCALABILITY_AND_LOAD_TEST_REPORT.md` (بارسنجیِ
کیف‌پول و مسیرِ پیام و کاوشِ ۵۰۰ فروشگاه)، `TEST_RESULTS.md` (عددِ هر اجرا) و
`docs/deployment-playbook.md` (نسخهٔ تفصیلیِ همین راهنما برایِ کسی که می‌خواهد واردِ جزئیات شود).

عددهایِ زیر در محیطِ توسعه (۱۲ هسته، ~۷٫۶ گیگ رمِ دراختیارِ داکر، دیسکِ لوپ‌بک‌شدهٔ ویندوز) گرفته شده‌اند.
سرورِ واقعیِ NVMe معمولاً بهتر است، نه بدتر.

| چه چیزی | عدد | چگونه |
|---|---|---|
| عملیاتِ مالیِ کیف‌پول در ثانیه (سقفِ اشباع) | **۲۹۰ تا ۳۱۰** | اندازه‌گیری‌شده (۷ سطحِ همزمانی، ۳۰۰۰ درخواست در هر سطح، صفر خطا، صفر بن‌بست) |
| پیامِ کاملِ مشتری در ثانیه (سقفِ یکِ پروسه) | **≈ ۱۴۵** | اندازه‌گیری‌شده |
| تراکنشِ دیتابیس در ثانیه | **≈ ۲٬۰۰۰** | اندازه‌گیری‌شده (pgbench) ⇒ دیتابیس ~۱۳ برابرِ اپ توان دارد |
| statement به‌ازایِ هر پیامِ مشتری | **۲۹** | اندازه‌گیری‌شده و در تست قفل شده (سقفِ ۲۹) |
| کاربرِ فعالِ هم‌زمانی که کد پوشش می‌دهد | ~۸٬۷۰۰ (۱ پیام/دقیقه) · ~۴٬۳۵۰ (۲/دقیقه) · ~۲٬۱۷۰ (۴/دقیقه) | محاسبه از ۱۴۵ پیام/ثانیه با فرضِ مشخص |
| کاربرِ فعالِ هم‌زمان در تولیدِ واقعی | **~۴۰۰** با تأخیرِ ۳ ثانیه‌ایِ AI | محاسبه از سِمافورِ `AI_MAX_CONCURRENT_CALLS=40`: `۴۰ ÷ تأخیر` |
| تأخیرِ واقعیِ AI | **نسنجیده شده** | سنجشش یعنی هر فراخوانیِ واقعی از بودجهٔ تو؛ عمداً انجام نشد |
| ۵۰۰ فروشگاه هم‌زمان | مسیرِ پیام ~۸ پیام/ثانیه در برابرِ بامِ ~۱۲۰ ⇒ ~۱۵ برابرِ سرِ‌باز | اندازه‌گیریِ مستقیم با `scripts/scale_probe.py` (RTTِ تلگرام در آن محیط ۲۵۰ms شبیه‌سازی‌شده) |

**گلوگاهِ اول: CPUِ همان یک پروسهٔ پایتون، نه دیتابیس.** یعنی ارتقایِ اولِ درست این است (به ترتیبِ ارزان‌به‌گران):
۱) NVMe و رمِ بیشتر ۲) دیتابیس رویِ هاستِ جدا ۳) تنظیمِ اتصال‌ها ۴) بالا بردنِ سقفِ همزمانیِ AI و اندازه‌گیریِ
تأخیرِ AI ۵) وب‌هوک + پروسه‌هایِ جدا.

## ۹) تنظیماتِ «تا ۵۰۰ فروشگاه» (اعدادِ همین کد)

| چه چیزی | پیش‌فرض | برایِ ~۵۰۰ فروشگاه | اگر تنظیم نکنی |
|---|---|---|---|
| `BOT_REGISTER_CONCURRENCY` | ۲۴ | ۱۶ تا ۴۰ | بالاتر = بوتِ سریع‌تر ولی رشِ ۵۰۰ درخواستِ API از یکِ IP؛ پایین‌تر = چند ثانیه طول کشیدنِ رسیدنِ همهٔ ربات‌ها |
| `BOT_MEM_LIMIT` | `1g` | **`2g`** | هر اتصالِ ربات ۰٫۴ تا ۰٫۷ مگابایت ⇒ ۵۰۰ ربات ≈ ۲۰۰ تا ۳۳۰ مگابایت رویِ ~۲۱۰ مگابایتِ پایه؛ زیرِ ترافیکِ واقعی OOM |
| `stop_grace_period` | ۱۰ ثانیه (پیش‌فرض داکر) | **۳۰ ثانیه** (در فایل گذاشته شده) | خاموش‌کردنِ ۵۰۰ ربات چند ثانیه می‌برد؛ با مهلتِ کم هر دیپلوی با SIGKILL تمام می‌شود |
| `BOT_HEALTH_START_PERIOD` | ۴۰ ثانیه | ۹۰ ثانیه یا بیشتر | `/health` تا پایانِ بوت ۵۰۳ می‌دهد ⇒ کانتینر «unhealthy» دیده می‌شود در حالی که سالم است |
| `ulimits.nofile` | ۱۰۲۴ رویِ بعضی میزبان‌ها | **۶۵۵۳۶** (در فایل گذاشته شده) | هر فروشگاهِ polling یکِ سوکتِ باز دارد ⇒ `Too many open files` |
| `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` | ۲۵ / ۰ | ۲۵ تا ۴۰ / **همیشه ۰** | اندازه‌گیری‌شده: بازکردنِ `overflow=30` توان را از ~۱۳۶ به ~۴۸ سقوط داد |
| `max_connections` پستگرس | ۱۰۰ | ۱۰۰ کافی است (تک‌پروسه) | فرمولِ چندِ worker: `تعدادworker × pool_size + چند اتصالِ مدیریتی < max_connections` |
| `AI_MAX_CONCURRENT_CALLS` | ۴۰ | با سقفِ RPMِ ارائه‌دهنده هماهنگش کن | این سِمافور در عمل سقفِ پاسخ را تعیین می‌کند، نه دیتابیس |

سه چیزی که **لازم نیست** بکنی و خیلی‌ها اشتباه می‌کنند:
۱) `--scale bot=2` — بی‌فایده است: قفلِ ضدِ تکرارِ polling نسخهٔ دوم را عمداً بیکار می‌گذارد تا یکِ پیام دو بار
پاسخ نگیرد و کیف‌پول دو بار کم نشود. ۲) ایندکس/مایگریشنِ تازه برایِ همین مقیاس. ۳) دسته‌ای‌کردنِ آمارِ
گزارشِ شبانه (۱۰ کوئری به‌ازایِ هر گزارش ≈ ۲٫۸ کوئری در ثانیه؛ ریسکِ عوض‌شدنِ عددِ داخلِ گزارش نداشت‌ارزش).

راهِ درستِ افقی‌کردن: **وب‌هوک** (nginx/Caddy + HTTPS + دامنه، `RUN_MODE=webhook`، چند worker uvicorn، و
**یکِ پروسهٔ جدا** برایِ pollingِ بله و جاب‌ها). این بازطراحی می‌خواهد، نه فقط تنظیم.

## ۱۰) کلیدهای AI و خرجِ ماهانه

فرض‌هایِ صریح (خودت رویِ دادهٔ واقعی اصلاح کن): هر مشتریِ فعال ~۳ فراخوانیِ AI در دقیقه در اوج؛ هر
فروشگاه‌دار ~۸۰ پیامِ مشتری در روز؛ میانگینِ ۱٬۲۰۰ توکنِ واقعی؛ قیمتِ ارائه‌دهنده ۰٫۰۱۴ دلار به‌ازایِ هر
میلیون توکن؛ نرخِ فروش به فروشگاه‌دار ۵۰ تومان به‌ازایِ هر ۱۰۰۰ توکن. همه‌یِ سطرهایِ این جدول **تخمین/محاسبه**
است، نه اندازه‌گیری.

| مقیاس | فراخوانیِ AI در روز | توکن در روز | خرجِ ارائه‌دهنده | درآمدِ AI از فروشگاه‌دارها | کلیدِ پیشنهادی |
|---|---|---|---|---|---|
| ۲۰ فروشگاه | ~۱٬۶۰۰ | ~۲ میلیون | ~۰٫۰۳ دلار | ~۱۰۰٬۰۰۰ تومان | ۲ (اصلی + پشتیبان) |
| ۱۰۰ فروشگاه | ~۸٬۰۰۰ | ~۱۰ میلیون | ~۰٫۱۴ دلار | ~۵۰۰٬۰۰۰ تومان | ۲ تا ۳ |
| ۳۰۰ فروشگاه | ~۲۴٬۰۰۰ | ~۲۹ میلیون | ~۰٫۴۰ دلار | ~۱٬۴۵۰٬۰۰۰ تومان | ۳ تا ۴ + دو مدلِ پشتیبان |
| ۱٬۰۰۰ فروشگاه | ~۸۰٬۰۰۰ | ~۹۶ میلیون | ~۱٫۳۴ دلار | ~۴٬۸۰۰٬۰۰۰ تومان | ۵ تا ۶ + بالا بردنِ سقفِ همزمانی و پروسه‌ها |

**قاعدهٔ سرانگشتیِ تعدادِ کلید:** `سقفِ درخواستِ دقیقه‌ایِ ارائه‌دهنده ÷ درخواستِ دقیقه‌ایِ تو` + یکِ
کلیدِ پشتیبانِ ارزان. دو کلید از دو سرویسِ متفاوت از چهار کلید از یک سرویس می‌ارزد، چون اختلال/تحریم/بن‌شدنِ
اکانت را پوشش می‌دهد. برنامه خودش مدارِ قطع دارد: هر کلید/مدلِ خراب بعد از پنج شکستِ پیاپی شصت ثانیه کنار
گذاشته می‌شود و کلیدِ بعدی امتحان می‌شود (رفتارش در تست قفل شده).

**هشدارِ امنیتیِ همین بخش:** آدرسِ سرویس AI را فقط ادمینِ ارشد می‌تواند عوض کند و برنامه آن را به شبکهٔ داخلی
اجازه نمی‌دهد (آدرس‌هایِ لوکال/خصوصی/متادیتایِ ابر رد می‌شوند، حتی در شکل‌هایِ مبدّل مثلِ عددِ دسیمال یا هگز).
با این حال اگر روزی به مقیاسِ بالا رفتی، خروجِ سرور را هم با فایروال محدود کن — چون محافظتِ فعلی نامِ میزبان
را DNS نمی‌کند و «بندینگِ دوبارهٔ DNS» تنها راهِ دورزدنِ باقی‌مانده است.

## ۱۱) مانیتورینگِ حداقلی (همان اولِ کار)

```bash
docker stats --no-stream                     # CPU/رمِ همین لحظه
docker compose logs --since 10m bot | grep -E "ERROR|Traceback" | head
docker compose exec -T db psql -U postgres -d kasbokar -c "select count(*) from pg_stat_activity;"

df -h / ; free -h
```

سه نشانه که باید سریع واکنش بدهی: بالا رفتنِ `RestartCount` کانتینرِ `bot`، خطایِ `TelegramNetworkError` در
لاگ، و `unhealthy` ماندنِ بیش از دو دقیقه. `/metrics` با توکن (`METRICS_TOKEN`) باز می‌شود و شمارشگرهایِ
پیام، خطا و تأخیر را می‌دهد؛ برایِ شروعِ جدی همین را به Prometheus/Grafana بردار (تخمین: ۱۰ دقیقه کار).

## ۱۲) عیب‌یاری (نشانه ← علت ← کارِ درست)

| نشانه | علتِ محتمل | کارِ درست |
|---|---|---|
| `docker compose up` دیتابیسِ **خالی** می‌دهد | نامِ پوشه عوض شده و پروژهٔ داکر تازه ساخته شده | با `-p kasb-o-kar-hoshmand` اجرا کن یا نامِ پوشه/`name:` را برگردان. داده در حجمِ قبلی سالم است |
| کانتینرِ `bot` هر ~۳۰ ثانیه ری‌استارت می‌شود، `/health` ولی ۲۰۰ می‌دهد | سرور به `api.telegram.org` نمی‌رسد (DNS/IP بلاک) | `docker compose exec -T bot python -c "import socket;print(socket.gethostbyname('api.telegram.org'))"` — اگر آدرسِ خصوصی/بازنگشتی داد، سرور یا مسیرِ شبکه را عوض کن |
| برنامه با «فایلِ .env ناقص یا نادرسته» بالا نمی‌آید | `MAIN_BOT_TOKEN` یا `ENCRYPTION_KEY` خالی است | از BotFather و از تولیدِ کلیدِ تازه (فقط در نصبِ اول) پرش کن |
| توکن/رمزهایِ ذخیره‌شده در پنل بازخوانی نمی‌شوند | `ENCRYPTION_KEY` عوض شده | همان کلیدِ اول را برگردان؛ با کلیدِ تازه هیچ رمزِ قدیمی باز نمی‌شود |
| پیامِ مشتری جواب نمی‌گیرد ولی پنل کار می‌کند | کلیدِ AI تمام/خراب است یا سوییچِ AI خاموش | پنلِ ادمین ← استخرِ کلیدها و «🧪 تستِ AI»؛ مدارِ قطع را با لاگِ «مدارِ قطع» بررسی کن |
| مشتریِ بله‌ای جواب نمی‌گیرد | کلیدِ رونماییِ رباتِ بله خاموش است، یا توکنِ بله ثبت نشده، یا این رونوشت قفلِ pollingِ بله را ندارد | پنلِ ادمین ← «🟢 رباتِ بله‌یِ فروشگاه‌ها»؛ پنلِ فروشگاه ← «🟢 توکنِ بله»؛ در لاگ بگرد: «اتصالِ بله» |
| پرداختِ بله‌پی به حسابِ منِ پلتفرم می‌نشیند نه فروشگاه | فروشگاه فقط توکنِ درگاه را گذاشته و توکنِ رباتِ بله را نه | از «💳 پرداختِ آنلاینِ سفارش‌ها» هر دو خانه را کامل کن؛ پیامِ پنل همین را می‌گوید |
| گزارشِ شبانه/دوره‌ای دو بار می‌آید | دو رونوشت جاب‌ها را اجرا می‌کنند | جاب‌ها قفلِ جدا دارند؛ اگر دیدی تکرار شده، `docker compose ps` را بگیر و از `--scale bot>1` پرهیز کن |
| تست‌ها/سوئیت می‌خوابند یا عددِ عجیب می‌دهند | رباتِ زنده سرِ `TRUNCATE` قفل می‌سازد، یا کدِ دیسک با کدِ ایمیج فرق دارد | قبل ازِ سوئیت `docker compose stop bot` و بعد ازِ هر تغییر `docker compose build bot` |
| `/health` تا دو دقیقه اول ۵۰۳ است ولی کانتینر سالم است | مهلتِ سلامتِ کوتاه در ناوگانِ بزرگ | `BOT_HEALTH_START_PERIOD` را بالا ببر (بخشِ ۹) |

## ۱۳) چک‌لیستِ بیست‌دقیقه‌ای قبل ازِ اولین مشتریِ واقعی

1. `docker compose ps` هر دو سرویس `healthy` و `RestartCount=0`.
2. `/health` = ۲۰۰ و لاگِ polling بدونِ ERROR/Traceback.
3. `ADMIN_TELEGRAM_IDS` ست شده؛ پنلِ ادمین باز می‌شود.
4. «🧪 تستِ AI» سبز است و استخرِ کلیدها حداقل دو کلید از دو سرویس دارد.
5. بکاپِ دستی گرفتی و **یک‌بار بازگردانی‌اش کردی** (رویِ ماشینِ دیگر/کانتینرِ دیگر).
6. `alembic heads` یک خط دارد.
7. درِ پرداخت: اگر بله‌پی روشن است، «🧪 آزمایشِ بله‌پی» سبز باشد و مقصدِ پول را در پنلِ فروشگاه بررسی کنی
   (هر دو ورودیِ فروشگاه یا درگاهِ سراسری).
8. قیمت‌گذاریِ AI در پنلِ ادمین (`هزینهٔ هر ۱۰۰۰ توکن`) با نرخِ واقعیِ ارائه‌دهنده‌ات هم‌خوان است.
9. دامنه/گواهیِ SSL اگر وب‌هوک می‌خواهی؛ اگر polling است، پورتِ ۸۰۰۰ را بیرون باز نکن.
10. یکِ خریدِ آزمایشیِ واقعیِ بسیار کوچک (مثلاً ۱٬۰۰۰ تومان) انجام و **در دیتابیس تأیید** شود؛ بعدش دادهٔ
    آزمایشی را با مسیرِ درستِ پنل پاک/آرشیو کن.

## ۱۴) چه چیزی را هنوز نمی‌دانیم (و باید اندازه بگیری)

- **تأخیرِ واقعیِ AI و هزینهٔ دقیقِ هر پیام:** نسنجیده (سنجشش پولِ تو را خرج می‌کند). با یکِ هفته ترافیکِ
  واقعی از `/metrics` و جدولِ `ai_usage_logs` خودش به عددِ درست می‌رسی.
- **دو رونوشتِ هم‌زمان رویِ یکِ دیتابیس:** منطقِ قفل‌ها نوشته و تست شده، ولی رفتارِ واقعیِ دو پروسه در این
  محیط سنجیده نشده.
- **RTTِ واقعیِ تلگرام/بله:** سنجش‌هایِ مقیاس با RTTِ شبیه‌سازی‌شدهٔ ۲۵۰ms انجام شده‌اند؛ رویِ سرورِ مقصد دوباره
  اندازه بگیر (اینجا `getMe` واقعی در ۸۲۷ms و ۳۹۹ms سنجیده شد — یعنی عددِ قبلی محافظه‌کارانه بوده است).
- **۵۰۰۰ کاربرِ هم‌زمان:** ادعا نمی‌کنیم. «۵۰۰۰ اتصالِ باز»، «۵۰۰۰ درخواستِ فعال در ثانیه» و «۵۰۰۰ کاربرِ
  لاگین‌کرده» سه چیزِ مختلف‌اند و توانِ اندازه‌گیری‌شده‌یِ ما به هر کدام عددِ دیگری می‌دهد.
